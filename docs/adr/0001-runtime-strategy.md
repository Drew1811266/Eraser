# ADR-0001 · 运行时策略：Electron 外壳 + Python 引擎（参考实现）

- **状态**：**已采纳**（2026-11-20，方案 A）
- **日期**：2026-11-19
- **决策者**：项目负责人
- **影响面**：整体架构、工期、安装包形态

---

## 背景

参考仓库存在两套实现：功能完整的 Python 引擎（`src/`，约 9300 行核心逻辑）与骨架完成但引擎被掏空的 Electron 应用（`frontend/`，超分 4 个模型全部 `implemented:false`）。

需要决定 Windows 版的运行时形态。这个决策决定了后续 80% 的工作量分布，必须先定。

---

## 候选方案

### A. Electron 外壳 + Python 引擎 sidecar（**推荐**）

外壳用现有 React/Electron，引擎以 stdio JSON-RPC 子进程运行，Python 用 PyInstaller 冻结为 onedir。

- ✅ 算法零重写，4966 行调参逻辑原样保留 → **功能等价风险最低**
- ✅ 引擎可被替换：契约稳定后，可逐模块换成 ONNX/原生（`inpaintOnnx.ts` 已证明 LaMa ONNX 可行）
- ✅ 外壳现代化：Chromium 预览、成熟打包、自动更新
- ❌ 双运行时，安装包大（基础包 600 MB 起，含 CUDA 组件可达 3 GB）
- ❌ 进程间需要契约与生命周期管理（一次性成本）

### B. 保留 pywebview，仅重打包到 Windows（**最快**）

- ✅ 改动最小：替换 `native_player`、修 `window.py:213` 的 gui 分支、重建 ffmpeg 与 venv
- ✅ 最快拿到可运行的 Windows 版本（周级）
- ❌ 与你已明确的产品方向相反（README：「发布包不再依赖 Python/pywebview」）
- ❌ pywebview 在 Windows 走 WebView2，预览能力弱，仍需自建帧服务
- ❌ 打包/签名/更新链路都要重做一遍，且做完仍是"遗留技术栈"
- ❌ 冻结后的 torch + WebView2 组合的启动性能与兼容性问题较多

### C. 纯 TypeScript 重写（**仓库当前实际在做的事**）

- ✅ 单运行时、包小、启动快、长期最干净
- ❌ 需重写 4966 行计算机视觉逻辑（时序稳定、质量评估、候选帧选择、接缝校正、Viterbi 序列选择……）
- ❌ 超分引擎在 TS 侧**没有可行实现**：Real-ESRGAN/SeedVR2 需要 ONNX/GGUF 原生 runner，而 4 个模型至今 blocked 就是证据
- ❌ 工期以「季度」计，且中途无法交付可用版本
- ⚠️ 不是"错"的方案，而是**现在做会死**的方案

---

## 决策

**采用 A**，并同时确立两条约束：

1. **Python 是「参考实现」，不是「最终形态」。** 契约层一旦稳定，任何引擎都可在不改 UI 的前提下被替换。LaMa 的 ONNX 路径已验证可行，作为第一个替换目标。
2. **禁止在引擎里新增 UI/平台假设。** 所有 OS 差异收敛到 `engine/platform/`。

> 方案 B 作为「如果 Windows 版必须在 3 周内可用」的应急预案保留；它的产物可以作为方案 A 的功能对照基线（golden reference），**不浪费**。

---

## 后果

**正面**
- 首个 Windows 可用版本可以在 **4–6 周**内产出（P0–P3），而不是数月。
- mac 版与 Windows 版共用同一引擎，行为一致性天然保证。
- 未来若要把某条链路换成原生实现，只需满足契约 + 通过黄金样本测试。

**负面 / 需要接受的代价**
- 安装包大，需要「主程序瘦 + 模型/加速按需下载」的分发策略。
- 需要维护一份 Python 运行时的打包链（PyInstaller + 依赖裁剪）。
- 双语言仓库对新人门槛略高；用契约生成物与烟雾测试来抵消。

---

## 附：为什么不建议"先纯重写、再补功能"

`frontend/` 已经重写了 6 个月以上的迹象（版本号 0.2.0、mac dmg 配置完整、CI 脚本齐全），但能力反而从"能用"退化到"LaMa 单点可用、超分全阻塞"。

这说明：**重写不是把功能搬过去，而是把功能重新调一遍参。** 在缺少黄金样本回归的情况下，重写会持续制造"看起来完成了、实际效果更差"的中间态。先锁契约、再用契约做替换，才是可控的顺序。
